# **2026-07-14 — Indentation and Space Breaks (Ticket 109)**

----------------------------------------------------------------------------------------------------


## **What we worked on**

Paragraph indentation and thematic breaks (`<hr/>` / “Space Breaks”) for EasyPub, aligned with [Standard Ebooks](https://standardebooks.org/) conventions.

**Ticket:** [109_Indentation-and-Space-Breaks.md](../2_Product-Overview-and-Requirements.md/3_Tickets/109_Indentation-and-Space-Breaks.md)

**PRD:** [PRD_1.7_Indentation-and-Space-Breaks.md](../2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.7_Indentation-and-Space-Breaks.md)


----------------------------------------------------------------------------------------------------


## **Research and planning (before implementation)**

- Reviewed SE Typography § Indentation and SE `core.css`: paragraphs indent `1em` by default; exceptions via CSS sibling selectors (`hr + p`, headings + `p`, `p:first-child`) and manual `class="continued"` after blockquotes (out of scope for v1).
- Documented indentation exceptions and export markup/CSS in the PRD.
- Clarified that a “space break” in print (gap + flush paragraph, no title) maps to SE’s **thematic break** — markup is `<hr/>`, not extra margin or empty `<p>`.
- Planned and wrote the ticket implementation plan: export CSS, viewer indent, `hr` as block type, `+` dropdown with four insert actions (text block / space break × above / below).


----------------------------------------------------------------------------------------------------


## **What was implemented**

### **Export**
- `easypub-styles.css` expanded in `3_App/server/index.js` with SE-style `p`, `hr`, and indent-reset rules.
- `hr` added to server allowed block tags.
- `add-block` supports `insertPosition: 'before' | 'after'`.
- New `add-space-break` queue action writes bare `<hr/>`.

### **Viewer**
- `3_App/src/views/reader/paragraphIndent.ts` — indent logic for `<p>` in view mode.
- `3_App/src/views/reader/addBlock.ts` — generalized insert before/after.
- `3_App/src/views/reader/addSpaceBreak.ts` — space break queue + optimistic UI.
- `TextBlock.tsx` — applies `textIndent: 1em` in view mode only; renders `<hr/>` blocks as non-editable centered label.
- `TextBlockToolbar.tsx` — `+` opens dropdown with four insert options; simplified toolbar for hr blocks.
- `Section.tsx` — passes `previousBlock` for indent calculation.
- `ReaderView.tsx` — parses existing `<hr/>`, wires handlers, spellcheck skips hr blocks.

### **UI polish**
- Space break label uses theme color `text-tertiary` (not `text-slate-400`).

## **Spellcheck in edit mode (Ticket 107) — completed**

Server-driven red underlines in TipTap edit mode via ProseMirror decorations (not browser spellcheck, not spell markup in the document).

**Ticket:** [107_Spellcheck-lines-not-displaying-in-edit-mode.md](../2_Product-Overview-and-Requirements.md/3_Tickets/107_Spellcheck-lines-not-displaying-in-edit-mode.md)

**PRD updates:** [PRD_1.6_Spellcheck-and-Dictionary.md](../2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.6_Spellcheck-and-Dictionary.md), [PRD_1.3_Viewer_and_Text_Block.md](../2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.3_Viewer_and_Text_Block.md) (spellcheck cross-ref)

### **Problem**
View mode showed server `.spell-unknown` underlines; edit mode relied on lazy browser spellcheck — no lines until the user typed a correction.

### **Solution (architecture)**
- **View mode:** unchanged — `block.spellcheckHtml` HTML spans
- **Edit mode:** plain `block.html` in TipTap + ProseMirror **decorations** from `/spellcheck-block` responses
- `spellcheck="false"` on editor; underlines hide while debounced re-check (~400ms) is pending
- Full decoration rebuild on each response — never stale position mapping

### **Key files**
- `3_App/src/components/viewer/richText/spellcheckRanges.ts`
- `3_App/src/components/viewer/richText/SpellcheckDecoration.ts`
- `3_App/src/components/viewer/richText/useEditModeSpellcheck.ts`
- `3_App/src/components/viewer/richText/TextBlockRichEditor.tsx`
- `3_App/src/views/ReaderView.tsx` — `fetchSpellcheckHtml` callback threaded through Viewer → Section → TextBlock

### **Rejected approach**
Initializing TipTap from `spellcheckHtml` or a `spell-unknown` mark inside the document model — would collapse the content/display boundary.

## **Table of Contents generation (Ticket 105) — completed**

Auto-generates `toc.xhtml` (EPUB3) and `toc.ncx` (EPUB2) on every save so ereaders can display navigation. Backend-only — no UI changes.

**Ticket:** [105_Table-of-Contents.md](../2_Product-Overview-and-Requirements.md/3_Tickets/105_Table-of-Contents.md)

**PRD:** [PRD_1.5_Table-of-Contents.md](../2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.5_Table-of-Contents.md)

### **What it does**
- `writeToc` in `server/index.js` runs unconditionally on every save, after `writeEndnotes` and before `writeOpf`.
- `collectTocEntries` walks the spine, extracts `<title>` text from each section xhtml (falling back to first heading, then filename), deduplicates, and appends an "Endnotes" entry if `endnotes.xhtml` exists.
- Generates both formats from the same entry list — `toc.xhtml` with `<nav epub:type="toc">` and `toc.ncx` with `<navMap>`/`<navPoint>`.
- Registers `toc.xhtml` in the OPF manifest with `properties="nav"`, and sets `<spine toc="ncx">` for EPUB2 compat.
- Full overwrite on every save — same pattern as endnotes.

### **Key decisions**
- Flat list (one entry per spine item), no heading-level nesting — SE's `se build-toc` handles that later.
- All spine items included (no filtering of titlepage, colophon, etc.).
- Sequenced after `writeEndnotes` so the "Endnotes" entry can be appended when applicable.
- Follows [Standard Ebooks ToC conventions](https://standardebooks.org/manual/latest/6-standard-ebooks-section-patterns).

## **Cover image backward-compatible normalization (Ticket 114) — completed**

On Update Epub, sync EPUB 2 + EPUB 3 cover declarations in `content.opf` when exactly one side is present, so library thumbnails and Finder/Explorer icons resolve more reliably (e.g. PocketBook).

**Ticket:** [114_Cover-image-backward-compatible-normalizaiton.md](../2_Product-Overview-and-Requirements.md/3_Tickets/114_Cover-image-backward-compatible-normalizaiton.md)

**PRD:** [PRD_1.2_Output-Standards.md](../2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.2_Output-Standards.md) — cover metadata section

### **What it does**
- `normalizeCoverMetadata(opfData)` in `3_App/server/index.js` runs on every Update Epub immediately before `writeOpf`.
- EPUB 3 only (`properties="cover-image"`) → add `<meta name="cover" content="<id>"/>`.
- EPUB 2 only (valid cover meta) → add `properties="cover-image"` to that manifest item.
- Neither / mismatch / multiple `cover-image` items → no-op. No file renames; no guessing from `cover.xhtml`.

### **Key files**
- `3_App/server/index.js` — `normalizeCoverMetadata`, helpers (`propertyTokens`, `getMetadataMetas`, etc.)
- `2_Product-Overview-and-Requirements.md/2_PRD/PRD_1.2_Output-Standards.md`
- Test fixture context: `4_testing/Do Artifacts Have Politics.epub` (had `cover-image`, missing EPUB 2 meta)
